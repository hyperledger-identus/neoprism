NeoPRISM Installation

NeoPRISM can be installed and run using either Docker or Nix. Choose the method that best fits your environment.

  • Docker installation: Run NeoPRISM using Docker containers.
  • Nix installation: Build and run NeoPRISM using Nix flakes.

Note: During development and testing, NeoPRISM typically uses between 10–100 MB of memory. No special hardware requirements are expected.

NeoPRISM also supports advanced deployment modes and Cardano data sources (such as DB Sync and testnet environments). For details on advanced configurations, see the relevant documentation pages.

Docker Installation

This guide will help you install and run a NeoPRISM node using Docker.

Prerequisites

  • Docker: Install Docker
  • Git: Install Git

Steps (Mainnet Relay Example)

  1. Clone the NeoPRISM repository:

    git clone https://github.com/hyperledger-identus/neoprism.git
cd neoprism/docker/mainnet-relay

  2. Start NeoPRISM and PostgreSQL using Docker Compose:

    docker-compose up

  3. Access the Web UI:

    • Open http://localhost:8080 in your browser.

  4. Resolve a DID using the API:

    curl http://localhost:8080/api/dids/<did>

Note: The example above demonstrates one way to run NeoPRISM using Docker. You can find additional deployment examples and configurations in the docker directory of the repository.

If you are deploying NeoPRISM in a production environment, please take extra care to harden your setup according to your organization’s security requirements.

Nix Installation

NeoPRISM can be built and run using Nix flakes.

Prerequisites

  • Nix with flake support enabled. See Nix Flakes documentation for setup instructions.
  • Git: Install Git

Steps

  1. Build the NeoPRISM binary from the remote flake:

    nix build github:hyperledger-identus/neoprism/<TAG>#neoprism-bin
    • The resulting binary will be located in ./result/bin/neoprism-node.

  2. Build the UI assets from the remote flake (in a separate output directory):

    nix build github:hyperledger-identus/neoprism/<TAG>#neoprism-ui-assets -o ./result-ui-assets
    • The UI assets will be available in ./result-ui-assets.

  3. Run NeoPRISM and link the UI assets:

    • Use the --assets-path flag to specify the UI assets directory:

      ./result/bin/neoprism-node indexer --assets-path ./result-ui-assets/assets [options]

    • For details on available commands and options, see the CLI help:

      ./result/bin/neoprism-node indexer --help

  4. Access the Web UI:

    • Open http://localhost:8080 in your browser.

NeoPRISM Architecture

NeoPRISM is a modular DID infrastructure for Cardano that can operate in multiple deployment modes:

  • Indexer: Reads and validates DID operations from the Cardano blockchain, storing them in the configured database backend (PostgreSQL or the embedded SQLite engine). When queried, it reconstructs the current DID state by replaying relevant operations and returns DID documents via its REST API.

  • Submitter: Receives signed DID operations and batches them into Cardano transaction metadata for publishing. This is a stateless process that does not manage private keys. It delegates transaction submission to a Cardano wallet component (currently cardano-wallet).

  • Standalone: Runs both indexer and submitter in a single process for simplified deployments.

Storage note: both the standalone and distributed layouts can point to PostgreSQL (recommended for production) or to the embedded SQLite file for local development. See database configuration for trade-offs and CLI flags.

Note: NeoPRISM does not manage keys for DID operations or Cardano wallets. Keys for DID operations are managed by the client that submits signed operations. Cardano wallet keys are managed by the cardano-wallet component.

Standalone deployment

In this mode, both the indexer and submitter run in the same process, making it suitable for small and simple deployment setups. You may also add a reverse proxy to handle authentication and routing for the submitter API paths.

Distributed deployment

In this deployment mode, the indexer and submitter run as separate processes, which may be hosted on different machines. This separation allows for independent scaling of each component; for example, multiple indexer instances can be deployed to support high read volume.

  • The indexer process reads, validates, and indexes DID operations from the Cardano blockchain, storing them in a shared database backend (PostgreSQL in production, SQLite for lightweight deployments).
  • The submitter process is stateless and receives signed DID operations, batching and submitting them to the Cardano blockchain via the wallet component. It does not use the database.

A reverse proxy is recommended to route requests to the appropriate service, handling authentication and API path routing for both the indexer and submitter.

Partial deployments

NeoPRISM also supports deploying only a subset of its components, depending on your use case and requirements:

  • Indexer-only deployment:
    Only the indexer process is deployed. This setup allows you to read, validate, and index DID operations from the Cardano blockchain, and serve DID resolution requests via the REST API. No submission of new DID operations to the blockchain is possible in this mode.

  • Submitter-only deployment:
    Only the submitter process is deployed. This setup allows you to batch and submit signed DID operations to the Cardano blockchain via the wallet component. DID resolution and indexing are not available in this mode.

These deployment options provide flexibility for scenarios where you may only need to resolve DIDs (indexer-only) or only need to submit new DID operations (submitter-only), without running the full NeoPRISM stack.

Note: These modes are subsets of the distributed deployment, and can be scaled or combined as needed.

SDK-Rust adoption

NeoPRISM reuses generic cryptography, DID syntax, DID resolution, and HTTP resolver mechanics from SDK-Rust. NeoPRISM remains the owner of PRISM operations, Cardano integration, persistence, service runtime, OpenAPI composition, and product policy.

This boundary reduces duplicate security-sensitive code without turning the generic SDK into a Cardano or NeoPRISM-specific component.

Compatibility contract

The SDK is authoritative for generic validation. NeoPRISM exposes explicit, fallible adapters where its established API differs:

  • empty optional arrays from legacy DID documents are omitted before SDK validation;
  • only the accept resolution option is supported; unsupported or unknown options fail with INVALID_OPTIONS instead of being ignored;
  • successful resolution responses honor the requested media type;
  • mismatched result and document DIDs are rejected;
  • Ed25519 public keys must have their exact encoded width;
  • the established Apollo/JVM secp256k1 fallback remains covered by compatibility vectors;
  • unknown extension error URIs use the SDK safe HTTP 500 fallback.

Adapters are migration boundaries, not copies of generic SDK behavior. New generic functionality belongs in SDK-Rust; PRISM, Cardano, storage, and product behavior belongs in NeoPRISM.

Dependency policy

SDK-Rust Git dependencies are declared once in the workspace and pinned to an immutable reviewed commit. Member crates inherit those declarations. Updating the pin is a deliberate integration change and requires the same local, protected-CI, review, and parity evidence as other adoption changes.

NeoPRISM’s Rust/Nix toolchain may remain newer than SDK-Rust’s baseline when the application requires it. The SDK baseline must not force the application to downgrade its own development environment.

Verification and acceptance

Acceptance requires all of the following against the exact candidate:

  1. formatting, workspace checks, strict Clippy, and focused crypto/DID/resolver tests pass locally;
  2. the repository Nix check passes without mutable dependency resolution;
  3. an independent Claude or Codex review has no unresolved blocker, high, or medium finding;
  4. every required protected GitHub check is green;
  5. native and cross-platform container builds are reproducible and runnable;
  6. the published baseline and SDK-backed candidate scan the same fixed Preprod boundary and produce equivalent indexed operations;
  7. scan duration, CPU, and memory evidence is recorded so QoS regression is visible;
  8. an independent engineer approves the pull request.

The reproducible old/new harness, commands, artifacts, and metric definitions are tracked in issue 325. The deterministic embedded-wallet packaging prerequisite is tracked in issue 326 and its implementation PR 348. The SDK adoption itself is reviewed in PR 324.

Rollback

Revert the adoption pull request. The compatibility facades keep the local API boundary explicit, and immutable SDK revisions make the previous dependency graph reproducible. A rollback must retain the parity artifacts and incident evidence rather than deleting them.

  • Status: Proposed for issue #345

Context

NeoPRISM currently owns both reusable PRISM method behavior and product/runtime behavior. Its identus-did-prism crate combines:

  • canonical and long-form DID syntax;
  • protobuf operation values and exact-wire hashing;
  • create, update, and deactivate validation;
  • deterministic DID state reduction and document projection;
  • VDR storage operations;
  • Cardano metadata, indexing, persistence-facing values, and resolver orchestration.

SDK-Rust now contains the separately releasable identus-prism-did crate at merged revision fe3a14b767a6b13f8aa2fb2acf92bc6e37d93c03. It owns only the portable method kernel: bounded syntax, exact signed-operation bytes, typed CRUD operations, deterministic state reduction, document projection, and a local long-form resolver. Private-key custody, Cardano, VDR storage behavior, persistence, HTTP, and node lifecycle are outside that crate.

PR #324 already establishes the generic SDK compatibility edge for crypto, DID values, DID resolution, and HTTP. Replacing NeoPRISM’s method behavior in the same PR would make review, rollback, and Preprod comparison too broad. Issue #345 therefore needs a second, adapter-first slice.

NeoPRISM does not currently preserve the exact signed-operation bytes at that boundary. Its Cardano sources decode PrismObject, and persistence re-encodes each SignedPrismOperation. Protobuf duplicate singular fields and unknown fields can therefore be lost before SDK parsing. NeoPRISM state also combines SSI state, VDR storage state, protocol-version selection, and ledger timestamps, while PrismDidState deliberately owns only the portable SSI substate. Both differences must be resolved explicitly; a package substitution cannot do so.

Decision

Adopt one immutable method kernel

NeoPRISM will consume identus-prism-did from one immutable SDK-Rust commit. The first implementation revision is selected only after PR #324 lands and must be recorded in Cargo.toml, Cargo.lock, the PR, and the parity receipt. All SDK crates used by one NeoPRISM revision must resolve from the same SDK-Rust commit.

SDK-Rust is authoritative for the supported Rust method profile. The pinned PRISM method specification is normative for protocol semantics. NeoPRISM, SDK-TS, and historical Apollo/JVM behavior are compatibility evidence, not authority over public Rust DTOs or errors.

Preserve the NeoPRISM boundary during the canary

The existing identus-did-prism package remains NeoPRISM’s public and runtime facade during the canary. Its method-facing modules delegate inward to identus-prism-did and translate explicitly at the boundary.

The facade may preserve deprecated NeoPRISM names temporarily, but no new SDK-facing type may use Apollo, Castor, Mercury, or other historical domain names. Generated protobuf types remain private on both sides and do not become the compatibility API.

Preserve exact bytes before SDK parsing

NeoPRISM will add a bounded observational scanner at the raw PrismObject metadata boundary. In legacy and shadow modes, the current protobuf decoder remains authoritative for the accepted block_content, operation set, and OSN ordering. The scanner aligns exact signed-operation slices with that decoded sequence. Duplicate block_content, empty/unknown operations, unknown fields, and alignment failure must not change legacy acceptance or renumber operations; they fall back to the current decode, mark the SDK shadow comparison non-comparable, and emit a bounded divergence metric.

sdk mode never consumes a re-encoded fallback row. Its re-index and live ingestion read raw chain-source bytes. An envelope that cannot be bounded, decoded, or aligned receives a specifically classified envelope rejection or the governance-approved catch-all rejection unclassified-envelope. The catch-all covers oversized, malformed, unknown, and non-aligning envelopes not matched by a more specific rule. Rejecting an envelope rejects all of its operations. It records the bounded ledger coordinate, reason, and safe digest but no derived operation/state mutation or unbounded attacker bytes.

Once an envelope is aligned, every exact signed-operation slice is parsed and validated independently in OSN order. A stable operation-level rejection, including duplicate signed fields, rejects only that operation; valid siblings continue through the reducer. ResourceLimitExceeded is the exception defined below: it quarantines that DID from its first failing operation onward. Envelope and operation rejection both advance the observed ledger cursor, emit bounded critical telemetry, and do not halt the indexer. Other valid transactions and DIDs in the same block continue. Only an internal invariant failure may stop ingestion; attacker-controlled syntax always maps to deterministic rejection. The catch-all and all specific rejection categories require protocol-governance approval before sdk mode can be promoted on a network.

For aligned operations, legacy mode continues to persist bytes produced by encode_to_vec; upgrading or enabling the default mode therefore does not silently change an existing storage/API contract. shadow keeps the exact slice only in its bounded in-memory index. The legacy path continues to decode and re-encode for its historical operation hash, operation ID, signature verification, DID grouping, derived index rows, and indexer API output. The SDK shadow alone uses exact bytes for those decisions. Any difference is evidence to classify.

sdk mode persists the exact aligned slice in raw_operation.signed_operation_data, but only in a clean candidate database built by the offline full-chain rehearsal and later selected atomically. It must not update production legacy rows through the current conflict-ignoring upsert, because that would mix exact and re-encoded rows. Before promotion, the implementation audits every reader of the field, including raw-operation parsing, database views, hash derivation, and the indexer HTTP API, and proves which representation each external response uses. Fixtures prove that legacy output is unchanged and that sdk output is reproducible from exact source bytes.

Exact-byte retention alone changes no database schema, but existing rows cannot prove their original encoding. Promotion therefore requires a clean full re-index from the immutable chain source. A database assembled from re-encoded legacy rows is not valid parity evidence. Any durable profile-limit quarantine marker introduced below uses a versioned migration when the existing schema cannot represent it. Duplicate security-relevant fields must reach the SDK scanner so its strict rejection remains effective. Fixtures cover duplicate block_content, duplicate signed fields, unknown fields, empty/unknown operations, scanner fallback, stable legacy OSN assignment, and clean cutover without mixed raw-row encodings.

Compose portable SSI state with NeoPRISM-owned state

PrismDidState replaces only the SSI method substate. NeoPRISM owns a composite shadow state containing:

  • the SDK SSI state;
  • existing VDR storage entries and their terminal/head relationships;
  • ledger-derived key/service creation and revocation timestamps; and
  • the active protocol-version processor.

The composite applies operations in ledger order. SSI operations first update a cloned SDK state and then update ledger metadata sidecars. Storage operations remain NeoPRISM-owned and verify against the active VDR key exposed by the SDK SSI state. DID deactivation commits atomically with the existing storage-entry revocation cascade. Protocol-version updates change only the NeoPRISM processor. Any failure leaves the whole composite unchanged.

This composite is an adopter adapter, not a second method implementation. It may be deleted only after the corresponding SDK VDR/indexer capabilities are adopted in later issues.

Use dual-path differential execution before deletion

The first implementation keeps the legacy method path as the only writer of production legacy tables. A did-method-engine configuration key accepts legacy, shadow, or sdk and defaults to legacy. shadow reads the same exact raw operation stream, executes the SDK composite in memory, records comparison telemetry, and never mutates persisted derived state. It builds a separate in-memory DID/operation/VDR index from exact bytes instead of querying legacy-derived DID or hash rows.

The shadow runs in an isolated, supervised worker with bounded non-blocking input, entry, raw-byte, and estimated retained-memory budgets. Budget accounting happens before allocation. Queue saturation, budget exhaustion, worker failure, or an unwinding panic disables comparison, marks the remaining range non-comparable, and emits bounded critical telemetry; it never blocks, applies backpressure to, or changes the result of legacy ingestion. Production builds must preserve an isolation mechanism that cannot turn a shadow panic into a process abort. Tests inject queue saturation, budget exhaustion, and worker failure while proving that the legacy cursor continues.

Because this first shadow index is not persisted, every shadow start or late enablement rebuilds it from the immutable chain source starting at the agreed network origin before reporting comparisons. It never bootstraps from legacy raw or derived rows. The #325 promotion receipt comes from one uninterrupted, complete origin-to-tip scan; a restart invalidates that receipt and starts a new run. Peak shadow memory and all configured budgets are part of its QoS evidence.

Pre-promotion node startup rejects did-method-engine=sdk. After promotion, sdk startup requires a durable selected-candidate record in guarded deployment configuration outside the candidate database. It contains the candidate’s backend identity, network, SDK/NeoPRISM revisions, schema/migration digest, the immutable #325 parity-baseline range and manifest digests, and a separate cutover cursor C with deterministic ordered-operation, acceptance, composite-state, and projection manifest digests through C. Absence or mismatch in either receipt fails closed before migrations, listeners, or ingestion. The fixed #325 receipt remains the independently reviewed parity/QoS baseline; it is not relabelled as evidence for a later cursor.

The record is signed by a cutover authority whose verification key is pinned outside the candidate database. Rehearsal cannot write guarded deployment configuration. At cutover, the legacy writer stops after durably committing an explicit handoff cursor C; no second writer may advance the selected network while ownership is transferring. Before candidate replay, attestation, or selection begins, the deployment owner must durably activate a legacy ownership fence in guarded deployment configuration outside both databases. The fence survives host, container, and orchestrator restarts; prevents the legacy writer and listener from starting or serving; and revokes its database role or storage mount and serving route. Merely stopping a process or denying legacy access to the candidate is not a fence. The candidate replays exact source bytes through C, proves the ordered-operation, acceptance, composite-state, and projection manifests through C, and records C in the selection record. Rehearsal write access is then revoked before the authority opens the read-only snapshot, recomputes the identity and manifest digests, checks #325 and protected CI evidence, and signs the exact frozen record. No rehearsal or runtime identity may mutate candidate rows during attestation.

Failure recovery leaves that fence active while candidate ownership is uncertain. Only the cutover authority may release it, using a signed rollback authorization after candidate ingestion and serving are durably disabled and the restored or freshly rebuilt legacy backend is verified at its authorized resume cursor. Release atomically restores the legacy database/storage access, serving route, and restart permission; it cannot overlap candidate ownership. The cutover and rollback fixtures must inject a legacy-host restart during handoff and after SDK selection and prove that the fenced legacy writer and listener remain unavailable until an authorized rollback releases the fence.

During the initial handoff, resolution, listeners, and normal SDK ingestion remain unavailable until startup has verified the record and confirmed the candidate’s durable cursor equals C. A handoff-only SDK writer then atomically commits the immutable cutover-complete marker at C; it cannot process the successor of C in that transaction or before the marker is durable. Only after that commit may resolution become available and normal SDK ingestion resume at the successor of C. Later restarts verify the signed record, cutover-complete marker, and authorized post-cutover cursor history; they resume from the current durable cursor at or after C and do not require it to still equal C. Node startup therefore proves the immutable baseline without making normal progress unrestartable, and candidate contents alone cannot authorize serving. Runtime rows after C are normal post-cutover ingestion and do not rewrite that baseline. A failed catch-up, cursor mismatch, manifest mismatch, marker commit, or writer-handoff timeout leaves legacy ownership intact or restores it through the documented rollback route; it never serves the lagging candidate.

The baseline revisions and schema digest identify the candidate that was validated; they are not an accidental permanent ban on upgrades. Every later runtime binary requires a separate signed runtime authorization that references the immutable baseline receipt, exact allowed SDK/NeoPRISM revisions, network, and the previous and target schema digests. Normal startup never applies an unapproved migration. A guarded offline sdk-upgrade flow rehearses the migration on a snapshot, captures backup/rollback and invariant evidence, applies the approved chain with a migration-only role, and publishes a signed migration receipt.

The migration executor cannot sign either artifact. After migration it loses write access; an independent upgrade authority opens a read-only snapshot, recomputes the schema and evidence digests, and verifies that the migrated database through the pinned cursor equals the target runtime’s signed manifests before signing the receipt and runtime authorization with a separately pinned key. For the bounded profile-remediation exception below, this pre-authorization equality applies to unaffected DIDs; each affected DID must equal its target full-replay per-DID manifest through the actual cutover cursor C inside the atomic targeted cutover before commit. Authorizations carry a monotonic sequence and superseded/revoked revisions in guarded external configuration. Startup accepts only the latest non-revoked sequence and verifies the complete signed authorization/receipt chain from the baseline to the current schema and exact runtime revisions before listeners or ingestion. Starting an older authorization requires an explicit signed rollback authorization and its compatible restored snapshot; restoring a database backup alone is insufficient.

Every upgrade pins one immutable upgrade cursor and differentially replays both the currently authorized and target runtimes from network origin through that cursor on isolated clones. The upgrade authority signs the paired cursor, ordered-operation/acceptance digest, composite-state digest, and projection digest as a new link in the authorization chain; it does not compare a later tip directly with the older cutover baseline. Exact acceptance and composite- state equality permits an in-place behavior-neutral upgrade. A projection-only difference may use an explicitly signed non-semantic authorization only after classification as a presentation defect, API compatibility evidence, and release notes; it cannot hide an acceptance or internal-state difference.

A change in ledger acceptance, exact operation IDs, or composite SSI/VDR/ timestamp/protocol state is otherwise not an in-place upgrade: it requires protocol governance or version activation, a new isolated full re-index, and a new promotion baseline/cutover. The sole exception is an approved SDK profile- limit remediation for already quarantined DIDs. Its signed authorization names the profile revision, affected DIDs and first failing operations, proves exact manifest equality for every unaffected DID, and uses the targeted sole-writer replay/cutover defined below for each affected DID. It cannot change acceptance for a previously unquarantined DID. An unapproved build, broken chain, unexpected schema, or unexplained manifest difference fails closed.

A separate offline sdk-rehearsal command is the only pre-promotion SDK writer. It has no listener or service endpoint and can write only to a dedicated candidate database, never merely another schema in the production database. The command requires both production and candidate connections, compares backend-owned immutable identities rather than connection strings, and refuses equal identities. Rehearsal re-indexes and quarantine migrations never modify production legacy tables. Backend isolation is explicit:

  • PostgreSQL: the production connection uses a read-only identity role with no table, schema, migration, or role-management writes. A candidate writer role is provisioned out of band with privileges limited to the candidate database; rehearsal never holds cluster-global role-creation credentials. Identity is the tuple of PostgreSQL system identifier, database OID, and a generated database UUID, allowing another database in the same cluster while detecting endpoint aliases.
  • SQLite: the live production identity connection opens with normal mode=ro locking and change detection so WAL-backed legacy writes remain visible and consistent. immutable=1 is permitted only for a frozen, checkpointed or SQLite-backup snapshot that includes a consistent WAL state and cannot be modified for the lifetime of the connection. The candidate is a separate file on a candidate-only volume; canonical path, device/inode identity, and a database UUID must all differ from the production file. Filesystem ownership permits rehearsal/SDK writes but denies the legacy deployment access to the candidate volume.

The rehearsal writer initializes only candidate-local identity and manifest metadata; neither is a selection authority. When sdk is enabled for an approved network, it serves only after that candidate has been rebuilt from exact source bytes, caught up through the stopped legacy writer’s handoff cursor C, validated at C, bound to the externally signed selection record, and atomically selected. Selecting the candidate database and transferring writer ownership at C is the promotion/cutover event, not a pre-promotion evidence step. Resolution stays unavailable across that bounded handoff; the system does not serve either an older candidate or the legacy database after SDK ownership is selected. For SQLite the selection record remains outside the database file, so the cutover authority never needs write access to candidate rows.

Candidate endpoint/role credentials or SQLite volume access are never provisioned to legacy deployments, including already-published binaries. Network, database, and filesystem controls reject legacy access to the candidate. The promotion and rollback receipts prove this separation; rollback points the legacy deployment only at the restored or freshly rebuilt legacy endpoint/file.

For every operation in the shared supported profile, the harness compares:

  1. parse outcome and stable error category;
  2. exact operation hash and operation ID;
  3. ordered state transition outcome;
  4. terminal composite state, including SSI state, storage state, timestamps, and protocol version, but excluding presentation projection;
  5. projected DID document through its separate projection digest; and
  6. deactivation and unsupported-version behavior.

Differences are classified as:

  • spec correction: SDK behavior follows the pinned specification but changes ledger acceptance; promotion stops until PRISM protocol governance approves the rule for all implementations or activates it through a protocol version;
  • historical compatibility requirement: ledger evidence requires a bounded compatibility rule in SDK-Rust;
  • NeoPRISM presentation defect/dead behavior: projection, error text, or telemetry differences that cannot change whether an operation is accepted may be corrected with evidence and release notes. Every acceptance difference still requires protocol governance or version activation.
  • SDK profile limit: finite SDK resources would make an otherwise accepted DID unresolvable. Promotion requires zero occurrences in the complete history of the target network and explicit network/profile approval. After promotion, any new occurrence fails closed, emits a critical metric/alert, and must not skip the operation or fall back to stale state. The failure is isolated to that DID: the raw operation and DID association are recorded, the ledger cursor advances, other DIDs continue indexing, and resolution returns a stable profile-limit-exceeded error from the first failing operation onward. Every later operation for the quarantined DID, including storage and deactivation operations, is retained as raw evidence but does not mutate its derived SSI or VDR state. The last good derived state is never served as current. A durable quarantine marker identifies the first failing operation; restart and re-index reproduce it deterministically. Raising a limit does not resume incrementally: a governed profile revision triggers a targeted origin-to-tip replay for that DID (or a full network re-index) using the recorded protocol-version timeline. Resolution continues returning the error while replay and live catch-up run. Final cutover executes inside the sole ingestion writer’s ordering. It locks the DID and fixes the global indexer’s committed cursor C. Before commit, an isolated target replay consumes every retained raw operation through that same C; its per-DID manifest must equal the staged replacement. Only then does the transaction replace every DID- derived SSI row, VDR row, key/service timestamp sidecar, and projection, record C, and clear the quarantine marker. A mismatch rolls back the whole transaction, retains quarantine, and emits a critical alert. An operation ordered after C is processed normally only after that transaction; no cursor gap can be skipped. Resolution resumes only after the complete cutover succeeds. If replay still exceeds the revised profile, no derived state is replaced and the marker atomically moves to the first operation that fails under that profile. The global protocol-version processor is not replaced by a DID replay.

No donor code is deleted merely because unit tests pass.

Keep security and resource invariants at the SDK edge

The adapter must preserve the SDK invariants:

  • signature verification and hashes consume the exact bounded nested operation bytes received on the wire;
  • duplicate security-relevant protobuf fields are rejected;
  • Ed25519 and X25519 public keys require exact widths;
  • the Apollo/JVM secp256k1 compatibility fallback remains covered by the pinned 50-vector suite;
  • update actions are ordered and atomic, retired identifiers cannot be reused, and active limits do not count tombstones;
  • long-form and projection limits are enforced before attacker-controlled allocation or work; and
  • authentication, authorization, and previous-operation linkage are verified before a state-growth limit can quarantine a DID;
  • ResourceLimitExceeded fails current resolution and shadow processing from the first failing operation onward; an immutable earlier version may resolve only when the public API explicitly supports versioned resolution. The error is never mapped to NeoPRISM’s legacy skip-invalid-operation path; and
  • errors crossing public/HTTP boundaries remain stable and redact sensitive bytes.

The adapter may narrow an SDK capability that NeoPRISM cannot honor. It must never silently accept and ignore an SDK option or operation.

Measure operational parity before switching the default

Issue #325 is the Preprod promotion gate. The published legacy node and the SDK-backed candidate scan the complete agreed immutable Preprod history and produce comparable ordered operation, composite-state, and projection manifests. The receipt also records scan duration, CPU time/utilization, peak resident memory, exact binaries/images, revisions, configuration, network, range, and host characteristics.

The SDK-backed path becomes the default for a specific network only when:

  • operation, composite-state, and projection parity is exact at the agreed boundary;
  • every non-comparable scanner occurrence in the complete target-network history is either eliminated by an exact-byte adapter improvement or classified and resolved through the same presentation, compatibility, protocol-governance, or profile-limit rules; unresolved occurrences block promotion;
  • every acceptance difference is either removed or activated by an approved network-wide protocol-version decision, not a local NeoPRISM migration;
  • QoS change is understood and accepted;
  • exact-head protected CI and independent review are green;
  • a rehearsal full-chain re-index has produced exact raw-operation storage and SDK-derived index rows in an isolated candidate database, plus a versioned quarantine migration when required, without modifying production legacy tables;
  • a read-only candidate snapshot reproduces the #325 ordered-operation and composite-state/projection manifest digests at the fixed parity boundary, then separately reproduces the cutover manifests through C; the signed selection record binds both receipts to the exact backend identity, schema, revisions, network, and their respective source cursors after rehearsal write access is revoked;
  • the complete pre-cutover legacy schema/data snapshot is captured and tested, or the clean legacy re-index route and immutable source are confirmed, before the candidate database can be selected; and
  • the rollback receipt covers a code revert plus either restoration of the complete pre-cutover legacy schema/data snapshot followed by replay from that snapshot’s cursor, or a clean legacy re-index from network origin into a fresh legacy schema. The legacy binary never opens or writes SDK-cutover tables.

The #325 receipt authorizes Preprod only. Mainnet remains on legacy until a separate complete Mainnet shadow receipt and explicit promotion decision satisfy the same operation, composite-state, profile-limit, QoS, re-index, and rollback criteria.

Consequences

  • NeoPRISM can shrink toward Cardano adapters, persistence, service composition, and operations without making the migration irreversible.
  • Temporary method duplication is intentional and measurable.
  • The compatibility facade and composite shadow state add temporary translation code, but isolate product effects from portable method behavior.
  • Exact-byte persistence and SDK-derived index rows require a full target-network re-index before promotion. Existing table definitions can be reused only in the isolated candidate database; a durable quarantine marker may require a versioned migration there.
  • A protocol correction that changes accepted ledger history cannot be shipped as a local migration.
  • identus-prism-vdr and identus-prism-indexer adoption remain independent milestones with their own operational evidence.

Alternatives rejected

  • Replace the whole did-prism crate at once: mixes portable method, storage, Cardano, and runtime behavior and makes parity failures hard to isolate.
  • Copy the SDK implementation back into NeoPRISM: restores duplication and defeats independent SDK release/adoption evidence.
  • Expose generated protobuf DTOs as the adapter contract: couples public APIs to one runtime and risks decode/re-encode security errors.
  • Treat SDK-TS or the old Rust implementation as normative: freezes donor DTO/error choices and known deviations instead of following the specification.
  • Delete the legacy path before Preprod comparison: removes the differential oracle and makes rollback operationally expensive.

Rollback

Before promotion, select did-method-engine=legacy and remove the read-only shadow adapter; no SDK-derived database rows or exact-slice replacements exist in the production legacy tables, and legacy storage/output semantics remain unchanged. The unselected rehearsal candidate is discarded or remains clearly marked unselected and is never opened by the legacy binary; it must be rebuilt or fully revalidated before any later selection. After promotion, rollback never runs the reverted binary against the SDK-cutover database. It requires a code revert plus either restoration of the complete pre-cutover legacy schema/data snapshot followed by replay from its recorded cursor, or a clean legacy re-index from network origin into a fresh legacy schema. Migration forward/backward compatibility may be tested as supplemental evidence, but never authorizes in-place rollback or replaces either clean rollback route. Changing SDK public method semantics requires an SDK-Rust issue and ADR; NeoPRISM must not carry an unreviewed local fork.

DLT Source Comparison

Oura

Oura works by performing a chainsync protocol with a Cardano relay node. This setup is quite lean, as you can connect to any available public relay. The downside is that sync progress can be slow, since it performs a full sync from the blockchain. If possible, connect to a Cardano node close to your location, as syncing across different geographic regions can be very slow. The initial sync may take multiple days. The best option is to connect to your own Cardano node within the same network for optimal performance.

DB Sync

DBSync is a service that syncs the Cardano blockchain and writes the data to a PostgreSQL database. DBSync is known to be resource-heavy and requires significant disk space. The advantage is that sync speed is very fast, since NeoPRISM only needs to read the database tables and parse the operations. If you can afford to run DBSync, it is recommended to use this option, as the initial sync is much faster compared to Oura.

Blockfrost

Blockfrost is a hosted API service that provides access to Cardano blockchain data without requiring you to run your own infrastructure. This is the easiest option to get started with as it requires no Cardano node, DB-Sync instance, or relay connections.

To use Blockfrost, you need to obtain an API key from blockfrost.io. The free tier is sufficient for most development and testing use cases.

How Common DLT Source Configuration Works

NeoPRISM streams blocks from the Cardano blockchain and extracts PRISM metadata, which is then persisted to the database. These operations are initially stored as raw, unindexed data. At every configured interval (set by the index interval option), NeoPRISM wakes up and picks up unindexed operations from the database. It then runs the indexing logic, which extracts, validates, and transforms each raw operation into an efficient lookup data structure.

A faster index interval reduces the lag between when an operation is streamed and when it becomes indexed and available for fast lookup. However, setting a very short interval can put additional pressure on the database due to more frequent indexing cycles. NeoPRISM comes with a sensible default value for the index interval to balance performance and resource usage.

Choose the DLT source and interval settings that best fit your infrastructure and performance needs.

Logging

NeoPRISM uses structured logging to help you diagnose issues and monitor node activity. Logging is powered by the tracing crate, and log verbosity is controlled via the standard RUST_LOG environment variable. By default, NeoPRISM outputs all logs to stdout.

Configuring Logging

To set the log level, set the RUST_LOG environment variable before starting NeoPRISM. For example:

RUST_LOG=info

Supported log levels (in increasing verbosity) are: error, warn, info, debug, and trace.

You can also filter logs by module. For example, to see only HTTP-related logs at debug level:

RUST_LOG=neoprism_node::http=debug

Multiple filters can be combined:

RUST_LOG=info,oura=warn,neoprism_node::http=trace,tower_http::trace=debug

About RUST_LOG

NeoPRISM uses the standard tracing environment variables to control log verbosity and filtering, including RUST_LOG. For more details on how RUST_LOG works and advanced usage, see the tracing-subscriber EnvFilter documentation.

Database Backends

NeoPRISM can persist indexed operations in PostgreSQL or in an embedded SQLite file. The backend is inferred from the NPRISM_DB_URL / --db-url scheme:

NPRISM_DB_URL=postgres://user:pass@host:5432/db
NPRISM_DB_URL=sqlite:///absolute/path/to/neoprism.db

If you omit NPRISM_DB_URL, NeoPRISM defaults to a SQLite database under your platform app-data directory (for example ~/Library/Application Support/NeoPRISM/<network>/neoprism.db on macOS).

Comparison

ModeRecommended usageProsTrade-offs
PostgreSQLProduction deployments or any scenario that needs horizontal scaling and concurrent writersBattle-tested RDBMS, works with existing replicas/backups, matches historical NeoPRISM behaviorRequires a managed Postgres instance; compose stacks need the extra container

PostgreSQL specifics

  • Provide NPRISM_DB_URL / --db-url in standard libpq form (postgres://user:pass@host:port/db).
  • The helper targets just postgres-up, postgres-down, postgres-dump, and postgres-restore spin up and manage a Dockerized Postgres instance for local work.
  • All pre-existing migrations live under lib/node-storage/migrations/postgres and continue to be linted via sqlfluff.
  • The Docker images and compose stacks ship with PostgreSQL enabled so existing deployments do not need any additional flags.

SQLite specifics

  • Provide NPRISM_DB_URL=sqlite://... (or --db-url) to point at a specific file, or omit it to use the default app-data location (for example ~/Library/Application Support/NeoPRISM/<network>/neoprism.db on macOS).
  • The helper commands just sqlite-init and just sqlite-clean manage migrations for the default file under data/sqlite/.
  • The parent directory is created with 700 permissions on Unix hosts to keep the file private.
  • SQLite enforces WAL mode automatically, but remember that only one process should write to the file at a time. Schedule periodic VACUUM runs if you prune large chunks of data.

Live Indexer Parity Test

The live parity harness runs a published NeoPRISM release and a candidate image against the same Cardano chain prefix. It is intended for release and migration evidence, especially when replacing internal components such as Apollo with sdk-rust.

The harness is read-only. It runs two Oura indexers and two isolated PostgreSQL databases, submits no transactions, and needs no wallet credentials.

nix build .#neoprism-docker-latest

just indexer-parity::run neoprism:sdk-rust-snapshot

Evidence and Exit Codes

Evidence is written beneath artifacts/indexer-parity/:

  • baseline.csv and candidate.csv contain normalized operation manifests;
  • report.json contains machine-readable differences and run metadata;
  • report.md is the review summary;
  • cursor-samples.csv contains elapsed time and both persisted cursors;

  • containers.log captures both indexers and databases.

Every invocation uses a unique Compose project, including when --keep is used, so retained or concurrent runs cannot share containers or database volumes. Every Docker/Compose/SQL subprocess is bounded by the run deadline; evidence capture and teardown use their own short finalization timeout.

The command exits with zero for equal manifests, one for a semantic difference, and two for configuration or harness failure. Containers and ephemeral database state are removed after the report is captured. Pass --keep to retain them for diagnosis.

The report summarizes total duration, live scan duration, time-to-boundary, effective cursor rate, average/p95/peak CPU, average/p95/peak memory, peak process count, and container restarts. It also calculates candidate-to-baseline ratios for the most useful comparative values. Change the five-second sampling cadence with --metrics-sample-seconds when needed.

Cost and Interpretation

Runtime depends on relay throughput and the selected boundary. Both images start from NeoPRISM’s fixed PRISM genesis point, not Cardano absolute genesis. The default timeout is two hours.

Resource telemetry is diagnostic. Docker CPU percentages may exceed 100% on multi-core hosts, and results vary with the runner, Docker runtime, relay, and other workloads. Establish a distribution from repeated runs on a controlled runner before defining a performance budget or making QoS metrics gating.

A passing report proves equality only through its recorded slot, with the Oura source and configuration shown in the report. It does not establish parity for DB-Sync, Blockfrost, or future operations beyond that boundary.

The Oura cursor is a source high-water mark, not a database-ingestion acknowledgment. To reduce the risk of stopping with queued events, the harness requires zero pending operations, stable manifest counts for the configured drain interval while both cursors remain at least two boundary lags beyond the comparison slot, then rejects the frozen exports if either contains a pending row. The report records the observed cursors, frozen operation and pending counts, quiescence duration, inspected image identities, and the exact image IDs used by the started containers. A PASS means persisted-manifest equality under bounded quiescence; it does not assert complete source ingestion. Until NeoPRISM exposes a persisted ingestion acknowledgment or an independent chain oracle is supplied, treat a single live run as bounded operational evidence rather than a mathematical proof that no source event was omitted. Repeated fixed-boundary runs and manifest agreement are required for promotion evidence.

Release Process

This document describes the step-by-step process for creating a new release of NeoPRISM.

Versioning

NeoPRISM follows Semantic Versioning (semver). The current version is stored in two places:

FileLocation
versionRepository root — single source of truth
Cargo.tomlWorkspace root — must match version

Prerequisites

Before starting a release, ensure you have:

  • Write access to the hyperledger-identus/neoprism repository
  • A GitHub personal access token with repo scope for pushing tags
  • Conventional commits — all commits in the release should follow the Conventional Commits standard. PR titles are validated against the conventional commits format by .github/workflows/pr-lint.yml (using amannn/action-semantic-pull-request@v6), and git-cliff uses conventional commit messages to generate the changelog automatically.
  • Nix — all release commands run inside nix develop

Release Steps

1. Ensure you are on the latest main branch

git checkout main
git pull origin main

2. Checkout the release branch

Create the release branch to the current main:

git checkout -b release

3. Bump the version

Run the automated version bump command from inside nix develop:

nix develop -c just release::bump-version

The release::bump-version recipe does all of the following automatically:

  1. Determines the next version — uses git-cliff to compute the next version based on conventional commits since the last tag
  2. Updates version and Cargo.toml — writes the new version to both files
  3. Generates the changelog — runs git-cliff to rebuild CHANGELOG.md from the commit history
  4. Regenerates Docker Compose configs — runs just build-config to update the auto-generated Docker Compose files with the new version

4. Commit the version bump

git add .
git commit -s -m 'chore(release): prepare for the next release'

5. Push and open a pull request

git push origin release

Open a pull request from release into main on GitHub. Once CI checks pass, merge the PR.

6. Create and push the tag

After the PR is merged to main, create a tag for the release and push it:

git checkout main
git pull origin main
VERSION=$(cat version)
git tag "v$VERSION"
git push origin "v$VERSION"

7. Trigger the release workflow

Note: The release workflow is triggered manually — it does not run automatically on tags.

Go to the Release workflow on GitHub Actions and click Run workflow. Enter the version number (without the v prefix) in the tag input field.

The workflow will:

  1. Check out the tagged commit
  2. Build Docker images for linux/amd64 and linux/arm64 using Nix
  3. Create a multi-arch Docker manifest and push it to Docker Hub under $DOCKERHUB_ORG/identus-neoprism:<VERSION>

8. Release the docs

Trigger the Deploy Docs Site workflow manually to publish the updated mdBook site to GitHub Pages.

9. Create a GitHub Release

Navigate to the Releases page and click Draft a new release. Select the v<VERSION> tag.

Optional: Curate the notable changes or highlight the breaking changes or other notes which require attention.

10. Verify the release

  • Docker Hub: Confirm the multi-arch image is available at docker pull $DOCKERHUB_ORG/identus-neoprism:<VERSION>
  • GitHub Releases: Confirm the release is published on the Releases page
  • Docs site: Confirm the updated documentation is live on GitHub Pages
